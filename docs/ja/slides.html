講義（Chapter 0・1）

依存の矢印は常に外側から内側へ向かう

ここでの「依存」は、自分たちが書いたパッケージ間の import を指す

domain は他に依存しない

他の層・Spring・JPA を参照せず、@Entity も付けない

usecase は domain のみ

adapter・framework を参照しない（@Service / @Transactional は実用上の例外）

adapter は内側のみ

domain と usecase だけを参照し、JPA Entity と Repository 実装もここに置く

Chapter 3 バックエンド実装

ドメインに業務ルールを閉じ込める

@JvmInline
value class Amount(val value: Int) {
    init {
        if (value <= 0) {
            throw DomainException(
              "金額は1円以上に設定してください。")
        }
    }
}

data class Transaction(
    val id: Long?,
    val category: Category,
    val title: String,
    val amount: Amount, /* … */
) {
    init {
        if (title.isBlank()) throw DomainException("…")
        if (title.length > 100) throw DomainException("…")
    }
}
  • 不変条件として、不正な状態の Transaction はどの経路でも作れない
  • 値オブジェクトとして、Int のままにせず Amount にする
  • JPA Entity は別のクラスにし、テーブル構造がドメイン設計に影響しないよう adapter で相互変換する
NG 例　domain に @Entity や @Component を付けると、第 1 層に外部技術への依存が生じる

Chapter 4 バックエンドのテスト

Konsist の dependsOn だけでは逆向き依存を防げない

domain.dependsOnNothing()
usecase.dependsOn(domain)
usecase.doesNotDependOn(adapter, framework)
adapter.dependsOn(domain, usecase)
adapter.doesNotDependOn(framework)
framework.dependsOn(domain, usecase, adapter)
  • dependsOn は依存してよい層の宣言で、宣言外の層への依存は禁止しない
  • 禁止できるのは dependsOnNothing と doesNotDependOn だけ

まとめ

実践した 4 つのこと

① 4 層の分離

ビジネスルール・手順・変換・技術詳細を分け、依存は外側から内側へ一方向にする

② 依存性逆転

usecase にインターフェースを置き、実装を外側から注入する（バックエンドもフロントエンドも同じ形）

③ 多層の自動テスト

JUnit・MockK・MockMvc・Vitest・MSW、そして Konsist でルール違反を自動検出する

④ AI に規約を守らせる仕組み

CLAUDE.md・rules・Skills・Hooks で、AI に規約を守らせながら実装と検証を進める
  • ルールは書くだけでなく、テストで検出させる
  • 依存方向の違反は、Konsist のアーキテクチャテストで自動的に検出する
