依存性のルール：矢印は常に外側から内側へ

ここでの「依存」は、自分たちが書いたパッケージ間の import を指します。

domain は孤立

他の層も、Spring・JPA も参照しない。@Entity も付けない。

usecase は domain のみ

adapter・framework は参照しない。
（@Service / @Transactional は実用上の例外）

adapter は内側のみ

domain と usecase のみ参照。JPA Entity・Repository 実装もここ。framework は参照しない。

ドメインに業務ルールを閉じ込める

@JvmInline
value class Amount(val value: Int) {
    init {
        if (value <= 0) {
            throw DomainException(
              "金額は1円以上に設定してください。")
        }
    }
}

data class Transaction(
    val id: Long?,
    val category: Category,
    val title: String,
    val amount: Amount, /* … */
) {
    init {
        if (title.isBlank()) throw DomainException("…")
        if (title.length > 100) throw DomainException("…")
    }
}
  • 不変条件：不正な状態の Transaction は、どの経路でも作れない
  • 値オブジェクト：Int のまま放置せず Amount に
  • 二重検証は役割分担：DTO の @NotBlank・@Positive は HTTP 境界、domain は自身の不変条件
  • JPA Entity は別物：テーブル構造がドメイン設計に影響しないよう分離し、adapter で相互変換
NG 例 domain に @Entity や @Component を付ける → 第 1 層が汚染される

0:50 – 1:10 ・ Chapter 4 バックエンドのテスト

Konsist：dependsOn だけでは逆向き依存を防げない

domain.dependsOnNothing()
usecase.dependsOn(domain)
usecase.doesNotDependOn(adapter, framework)
adapter.dependsOn(domain, usecase)
adapter.doesNotDependOn(framework)
framework.dependsOn(domain, usecase, adapter)
落とし穴
dependsOn は「依存してよい層」の宣言で、宣言外の層への依存は禁止しない。
禁止は dependsOnNothing と doesNotDependOn だけ。
注入する違反検出
domain → usecase の import検出（元から）
usecase → adapter の importdoesNotDependOn で検出
adapter → framework の importdoesNotDependOn で検出
早く終わった人の演習：Category.kt に @Component を付けてテストを失敗させる。※ Amount.kt（value class）に付けるとコンパイルエラーでテストまで進みません。

1:55 – 2:00 ・ まとめ

まとめ：今日実践した 4 つのこと

① 4 層の分離

ビジネスルール・手順・変換・技術詳細を分け、依存は外側から内側へ一方向。

② 依存性逆転

usecase にインターフェースを置き、実装を外側から注入。バックエンドもフロントも同じ形。

③ 多層の自動テスト

JUnit・MockK・MockMvc・Vitest・MSW、そして Konsist でルール違反を自動検出。

④ AI のガードレール

CLAUDE.md・rules・Skills・Hooks で、AI に規約を守らせながら実装と検証を進める。
最も効いた学び：ルールは「書く」だけでなく「テストで検出させる」。dependsOn の落とし穴のように、実際に違反を注入して検出を確かめるまでは安心できない。
