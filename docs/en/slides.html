Spring Boot

Spring Boot assembles a working server fast through convention over configuration

Auto-configuration

  • It inspects the classpath and prepares beans and settings
  • The entry point is @SpringBootApplication

Dependency injection

  • Spring creates objects and passes an implementation that matches the constructor type
  • Here it injects an Interactor into the Controller

Starters and embedded server

spring-boot-starter-* adds related dependencies together, and the embedded web server starts with just ./gradlew bootRun

Externalized config

Connection settings live in application.yml instead of the code
Spring's DI container "passes implementations in from outside", which fits the Dependency Inversion Principle of Clean Architecture

Next.js and frontend

Next.js uses file placement as convention and makes the server/browser boundary explicit

File-system routing

app/transactions/page.tsx becomes /transactions, and layout.tsx is the shared frame

Server Components by default

  • App Router components render on the server by default
  • Only parts that need state or events become Client Components

'use client' is the boundary

  • Adding 'use client' at the top makes that file and its imports run in the browser
  • Hooks and onClick work only there
  • Next.js decides how screens are delivered

domain depends on nothing

References no other layer, Spring or JPA, and carries no @Entity

Benefits in practice

Without layers, rules and the DB end up in one class

Anti-pattern example, not code from this hands-on
@RestController
class TransactionController(
  val jpa: JpaTransactionRepository
) {
  @PostMapping("/api/transactions")
  fun create(@RequestBody req: Map<String, Any>): Any {
    if ((req["amount"] as Int) <= 0)
      throw ResponseStatusException(400)  // business rule
    val e = TransactionJpaEntity(...)       // DB type
    return jpa.save(e)                      // direct DB access
  }
}
  • The amount rule lives in the Controller and is rewritten for the update API
  • Changing a DB column forces a Controller change
  • Tests need Spring and a DB, so they run slowly
  • The class grows with each feature and its impact is unreadable

// Input port, called by the Controller
interface CreateTransactionUseCase {

// Output port, called by the Interactor

  fun save(transaction: Transaction): Transaction

class CreateTransactionInteractor(
  private val transactionRepository: TransactionRepository,
  private val categoryRepository: CategoryRepository
) : CreateTransactionUseCase {
  override fun execute(input: ...): Transaction {
    val category = categoryRepository.findById(...)
      ?: throw DomainException("...")
    val transaction = Transaction(... /* amount = Amount(input.amount) */)
    return transactionRepository.save(transaction)
  }
}

Keep business rules inside the domain

@JvmInline
value class Amount(val value: Int) {
    init {
        if (value <= 0) {
            throw DomainException(
              "金額は1円以上に設定してください。")
        }
    }
}

data class Transaction(
    val id: Long?,
    val category: Category,
    val title: String,
    val amount: Amount, /* … */
) {
    init {
        if (title.isBlank()) throw DomainException("…")
        if (title.length > 100) throw DomainException("…")
    }
}
  • As an invariant, an invalid Transaction cannot be created by any path
  • As a value object, Amount is used instead of a bare Int
  • The JPA Entity is a separate class, converted in adapter so the table structure does not shape the domain

The 4-layer design has costs, and this hands-on simplifies some parts

Costs

  • Even a budget app needs 29 backend files
  • More type-conversion code
  • Can be overkill for small or short-lived apps

Simplifications here

  • Interactors carry @Service and @Transactional, so usecase depends on Spring
  • UseCases return domain models directly
  • Decide by business-rule complexity, lifespan, and team size
  • The team decides how much simplification to allow

Summary

Four things we practiced

① Four-layer separation

Separate rules, procedures, conversion and technical details, with dependencies pointing inward

② Dependency inversion

Interfaces sit in usecase and implementations are injected from outside, in the same way for backend and frontend

③ Layered automated tests

JUnit, MockK, MockMvc, Vitest and MSW, plus Konsist to detect rule violations

④ Making the AI follow rules

CLAUDE.md, rules, Skills and Hooks drive implementation and verification within the rules
  • Rules are not only written, tests also detect violations
  • Dependency direction violations are detected automatically by Konsist architecture tests
